# Lume — instruções para agentes e colaboradores

Antes de propor ou alterar comportamento do produto, leia nesta ordem:

1. [Regras de negócio consolidadas](docs/REGRAS_DE_NEGOCIO.md) — fonte única de verdade do produto, do estado v3, da política de XP v2, da Agenda, da importação e do que foi aposentado das versões v1/v2.
2. [Estado atual e pendências de implementação](docs/IMPLEMENTACAO.md) — mapa do que já funciona × o que falta implementar ou verificar em produção.
3. [Aplicativo de desktop](companion/README.md) e [Publicação e CI](docs/RELEASE.md), antes de mexer no pacote Electron (`companion/`) ou no workflow de release.
4. [Extensão do navegador](extension/LEIAME.md), antes de mexer na captura de cursos em `extension/` ou nos provedores em `public/providers/`.

Esses documentos descrevem o estado atual e as regras vigentes do Lume. Prevalência: instrução explícita da pessoa responsável > `docs/REGRAS_DE_NEGOCIO.md` > código e testes antigos. Mantenha a documentação enxuta e coerente com novas decisões.

## Comandos

Windows com ExecutionPolicy restrita: `npm.ps1`/`npx.ps1` falham; use `npm.cmd`/`npx.cmd` ou `node` direto.

```sh
npm run dev          # Astro em 4321 + API Node em 4173; LUME_API_PORT troca a API e o proxy acompanha
npm start            # build + serve dist/ em 4173 (PORT ajusta)
npm run preview      # só serve o dist/ existente
npm run build        # astro build + scripts/headers.mjs (gera dist/_headers com CSP)
npm test             # node --test nos arquivos listados em package.json
node --test tests/unit/auth.test.js
node --test --test-name-pattern="redefini" tests/unit/session.test.js
npm run test:e2e     # Playwright; exige dist/ e sobe o próprio servidor na 4187 (LUME_E2E_PORT troca a porta)
npx playwright test tests/e2e/session.spec.js --project=desktop
```

Não há lint, typecheck, formatter nem TypeScript configurados — não invente `npm run lint`/`tsc`. O projeto é JavaScript puro (`.js`/`.jsx`), `"type": "module"`, Node >= 22.23.4 (usa `node:sqlite`).

No CI, `PLAYWRIGHT_CHANNEL=bundled` força o Chromium baixado; localmente o padrão é o Chrome instalado.

## Arquitetura que não é óbvia pelos nomes

### Persistência direta da biblioteca (revisão de 03/11/2026)

- A conta usa `GET /api/library` e `POST /api/library/actions`, com operações por entidade, revisão otimista e idempotência; `api/domain/library-store.js` grava `materials`, `units`, `study_progress`, `study_tasks`, `study_sessions` e `account_documents` (esquema `0012_library.sql`). Materiais têm somente `units` no domínio, API v3 e banco. Listas/árvores são visualizações derivadas por `material-model.js`.
- Não reintroduza IndexedDB, fila offline, sincronização por cursor ou reconciliação de documentos no navegador. A prévia dura só na página aberta. Não há migração de dados: documentos antigos no servidor (`user_state`) são preservados como arquivo, nunca convertidos, e a conta entra com uma biblioteca nova e vazia (`ensureLibrary`); leituras compartilhadas devolvem estado nulo para eles. Backups só aceitam v3. Clientes antigos recebem `client_outdated` ao tentar gravar sobre uma biblioteca nova.
- Conclusões, conquistas e tempo elegível são preparados no servidor e gravados no mesmo batch da biblioteca (`library-actions.js`, `library-time.js`). A revisão aborta o batch inteiro em conflito. Repetir usa o mesmo id de operação; conflito pede recarga, sem mescla automática. Outra aba ou o aplicativo de desktop avançam a mesma revisão (16/11/2026): `useLibraryPersistence` confere a revisão ao voltar o foco e a cada minuto com a aba visível (`adopt`, sem gravação pendente), e gravações de fundo (`act(regra, { background: true })`: batimento da sessão, fechamento de sessão esquecida) adotam o estado do servidor em conflito em vez de bloquear. Ações da pessoa continuam pedindo recarga. `outbox.js` e `useProgressSync.js` foram removidos.
- As telas recebem ações nomeadas de `src/features/{account,library,plan,progress,settings}/actions.js`; `act` e o setter ficam privados em `useLume`. Cada ação aplica a regra de `public/` sobre o estado mais recente e devolve `null` quando a gravação está bloqueada: preserve o formulário e não anuncie sucesso. Telas e domínios leem `materialSteps`, `materialStructure` e `materialLesson`; o cache pressupõe objetos imutáveis. Não grave `steps`, `structure` ou `selection` em materiais. Biblioteca e diálogo usam `nextAction` do roteiro.
- `useLume` compõe `features/account/useAccountSession.js` (sessão e prévia), `features/library/useLibraryPersistence.js` (estado, revisão, envios serializados em memória e repetição) e `features/progress/useXp.js` (leitura do livro). O transporte e a aplicação genérica de regras ficam privados nessa composição, sem acesso pelas telas.
- **PDFs e disciplinas (11/11/2026):** disciplinas são a coleção `subjects` (`subject.put/delete/order`, tabela `study_subjects`, regras em `public/subject-domain.js`); materiais ganham `subjectId`. PDF anexado é material `type: 'pdf'` com `pdf` (metadados, sumário) e `reading` (página), uma etapa única, regras em `public/pdf-domain.js`. O arquivo vai por `PUT /api/library/files/:id` para R2/`data/media` (`api/domain/library-files.js`, cota em `library_files`, plano em `storage_plans`); nunca guarde o PDF no navegador. `library-actions.js` recusa material que aponte para arquivo inexistente e apaga o objeto ao excluir o material. Imagens e PDFs novos são otimizados no navegador (`public/compression-domain.js`, `src/lib/image-compress.js`, `src/features/library/pdf-compress.js`); PDF com texto só é re-salvo se páginas, sumário e texto continuarem iguais, e digitalização só é rasterizada sob escolha explícita. A tela Configurações › Armazenamento também otimiza arquivos existentes em `PUT /api/library/files/:id/replace` e `PUT /api/storage/items/social/:itemId/replace` (`replacePdf`, `replaceSocialAttachment`), atualizando tamanho e cota sem alterar material ou publicação. Avatar, capa e imagens de slides existentes são recomprimidos e reenviados por `PUT /api/profile/media/:slot` e `PUT /api/slides/media/:courseId/:slideId`, atualizando a URL no perfil ou na apresentação; essas imagens não entram na cota. A cota inicial é 10 MB por conta e por arquivo, unificada entre Biblioteca e Social. Abrir um PDF no leitor cria sessão `origin: 'reading'` (`useReadingSession`), com indicador visível, pausa após 5 minutos sem interação/aba oculta, escolha quando há sessão pausada e preferência `readingTimer`; `App.jsx` mantém o batimento de qualquer sessão ativa entre telas. O leitor usa `pdfjs-dist` carregado sob demanda (`src/features/library/pdf-client.js`); o worker é `.mjs` e precisa ser servido como JavaScript. IA só em `POST /api/library/identify`, sob pedido. Detalhes em [Regras de Negócio](docs/REGRAS_DE_NEGOCIO.md#4-biblioteca-materiais-unidades-e-disciplinas-estado-v3).
- Estilos por funcionalidade ficam em `src/features/<área>/*.css`, e a casca em `src/app/shell.css`. A identidade Norte (14/11/2026; [Regras de Negócio §1](docs/REGRAS_DE_NEGOCIO.md#1-diretrizes-gerais-e-identidade-do-produto)) vale para todas as telas pelos tokens; `today.css`, `shelf.css`, `timer.css`, `schedule-session.css` e `welcome.css` ficam ao fim de `lume.css`, e peças comuns (botões, `.soft-badge`, `.metric-label`, `.mono`) em `80-redesign-moderno.css`. A etapa 1 recompôs a casca e o Início (`features/library/Today.jsx`, derivações em `public/home-domain.js`); a etapa 2, as telas de estudo diário (Biblioteca, Disciplinas, Plano, Calendário, Tarefas e Agendar); a etapa 3, Social, Mensagens, Ranking, Perfil, Conquistas, Configurações, Onboarding, o e-mail de recuperação e os ícones do aplicativo de desktop. Capas de material não usam foto: `Cover` (`ui.jsx`) desenha uma constelação curta. Imagens usadas só por testes ficam em `tests/fixtures/`. Tema, tamanho do texto e XP visível se ajustam só em Configurações › Aparência; não há mais o botão "Conforto visual" no cabeçalho. Filtros e seletores usam abas de 10px com a ativa em papel (`.filter-btn`); cores de disciplina e de tipo de compromisso usam `--subject-*`, que só identificam e não têm função. Ritmo semanal e minutos por dia vêm de `minutesByDay`/`weeklyRhythm` em `public/session-domain.js`. `src/styles/` mantém tokens, base, shader, diálogos, responsividade e tema. **Celular (15/11/2026):** `90-celular.css` fecha a cascata com o que atravessa telas (campos com 16px para o iOS não ampliar ao focar, botões que quebram linha, abas e filtros em uma linha rolável de ponta a ponta com `--page-gutter`, diálogos como folha presa ao rodapé até 600px); o que é de uma tela fica na folha dela. Nenhuma tela pode passar da largura do celular — `html`/`body` cortam o excesso com `overflow-x: clip`, o que esconde o problema na emulação, e o teste `@celular` de `tests/e2e/pdf.spec.js` mede `#main`. Na barra inferior, destino com `short` em `SECTIONS` mostra o rótulo curto e mantém o nome completo como nome acessível. O leitor de PDF no celular ocupa a tela, com barra em duas linhas, sumário em gaveta e painel em folha inferior, fechado ao abrir. `src/styles/lume.css` importa tudo em ordem explícita; não acrescente imports nos componentes alterando a cascata por ordem de montagem.

- **SPA em uma única página Astro.** `src/pages/index.astro` monta `<App client:only="react" />` e define o service worker. As rotas são hashes resolvidos em React (`#hoje`, `#biblioteca`, `#tarefas`, `#agenda`, `#agendar`, `#aplicativo`, `#amigos?convite=`, `#perfil?id=`; `#conheca` é a apresentação pública, aberta sem conta como `#recuperar`) — criar tela é componente + uma linha na tabela `src/app/routes.jsx` (hash, título, seção e aba), não arquivo em `src/pages/`. O menu tem quatro destinos (`SECTIONS` com `nav` diferente de `false`: Início, Biblioteca, Plano de Estudos e Social; a tela Início é a antiga Hoje e mantém o hash `#hoje`, porque `#inicio` é o onboarding), num cabeçalho em vidro (barra fixa inferior no celular; o cabeçalho não pode ter `backdrop-filter` no celular, senão prende a barra). A seção Perfil (`nav: false`) abre pelo menu da conta, com as abas Meu perfil, Conquistas e Configurações. As abas de seção e o título da janela derivam da tabela; uma aba pode ter ícone (`tabIcon`). Plano de Estudos reúne Tarefas (aba padrão; `#plano` abre ela) e Calendário (`#agenda`, com as aulas previstas do cronograma na grade e o detalhe do dia abaixo dela); as duas telas desenham as abas abaixo do próprio cabeçalho (`hideTabs` na rota e `<SectionTabs/>` na tela), como no Stitch. `#agendar` pertence ao Plano sem aba própria. Não há tela de Foco: o timer é um controle discreto do cabeçalho (`features/progress/HeaderTimer.jsx`, desligável por `preferences.focusTimer`; no celular, botão flutuante só com sessão em andamento e início pelo menu da conta). Endereços antigos viram apelidos (`ALIASES`): `#plano`, `#missoes` e `#roteiro` abrem Tarefas, `#foco` abre o Início, `#historico` abre Conquistas. `src/app/App.jsx` resolve a rota e os diálogos (`src/app/modals.jsx`); telas ficam em `src/features/<área>/` e componentes visuais em `src/ui/`. Para gravar, use a ação nomeada da funcionalidade; não exponha setters do estado inteiro às telas. Recursos compartilhados (amigos, ranking, não lidas, conversas, cartão da pessoa, Desktop) passam por `useResource` (`src/lib/resources.js`), com cache, revalidação ao montar e intervalo compartilhados. O estado do cliente passa por `src/app/useLume.js` e as chamadas HTTP por `src/lib/api.js`. Estilo em `src/styles/` (um arquivo por seção, importados em ordem por `src/styles/lume.css`).
- **Social (16/11/2026):** as quatro abas (Feed `#amigos`, Mensagens, Ranking, Amigos `#adicionar`) usam `SocialFrame.jsx` (cabeçalho, abas e largura iguais; as rotas têm `hideTabs`). Nome ou foto de pessoa abre `PersonButton`/`PersonCard.jsx` (`GET /api/people/:id`); não crie outro jeito de abrir alguém. **Perfil (16/11/2026):** a parte de cima (capa, foto, nome, @usuário, presença, biografia, botões) fica como está; a de baixo (`ProfileSections.jsx`) tem duas colunas — abas Atividade (um cartão por material) e Publicações (as da pessoa, com fixada em `profile_pins`) e a lateral Nível, Conquistas e Amigos. A privacidade é uma chave geral (aberto/privado) e o alcance por seção (Todos = conta logada, Só amigos, Só eu) em `public/privacy-domain.js`; o servidor confere cada seção em `readProfileAccess` (`api/domain/friends.js`), inclusive lista de amigos, publicações, anexos e contadores. As chaves antigas `preferences.sharing` ficam só por compatibilidade. Feed, reações e comentários continuam só entre amigos. "Estudando agora" (Feed) e "Ativos agora" (Início) vêm de `ActiveFriends.jsx`. Mensagens são três regiões com altura calculada pela janela (`useFillHeight`); no celular, uma por vez. Imagem em mensagem não existe (falta decidir como liberar a cota). Regras em [Regras de Negócio §10](docs/REGRAS_DE_NEGOCIO.md#10-social-amigos-perfil-mensagens-e-ranking).
- **Agenda:** leia [Regras de Negócio §8](docs/REGRAS_DE_NEGOCIO.md#8-agenda-calendário-e-lembretes-publicagenda-domainjs) antes de alterar calendário, recorrência ou lembretes. `public/agenda-domain.js` guarda regras; `agenda_entries` persiste ocorrências com referências às tarefas existentes. `appointment.put/delete/order` usa o batch da biblioteca. Lembretes são reivindicados uma vez por conta por `POST /api/agenda/reminders`, com revisão transacional e tabela `agenda_reminders`. A Agenda não entra no perfil social. Encerrar atividade não conclui tarefas nem gera XP; recorrência não repete recompensa de aula. Notificações exigem site/app executando e rede; no Electron, preservar `backgroundThrottling: false` para a janela minimizada. Verificação nativa: `node scripts/test-agenda-desktop.mjs` (build e dependências de `companion/` necessários; conta e configuração isoladas).
- **Calendário interativo:** FullCalendar Standard 7 em `features/agenda/Agenda.jsx`; CSS externo no manifesto `lume.css`, cores por tokens. `calendar-model.js` converte instantes para o fuso original ao arrastar; datas sem horário permanecem civis. No mês, arrastar escolhe apenas o dia e remove o horário do bloco (`calendarPatch(..., { month: true })`). O motor visual não persiste nem gera recorrência. `saveAppointment` grava checklist e compromisso juntos; falha de gesto abre o editor, série exige escopo antes de gravar. A tela mostra só a visão mensal (Dia, 3 dias, Semana e Lista foram retiradas por decisão da responsável); horário se define no editor do compromisso. Nada acima da grade pode mudar de altura depois de montada (avisos flutuam): o FullCalendar guarda posições e o arrasto quebraria. Mover e excluir oferecem Desfazer pelo `notify(message, { action })` de `App.jsx`.
- **Regras de domínio ficam em `public/*.js`** (`domain.js`, `material-model.js`, `progress-domain.js` — registro único de progresso do estado v3, `import-domain.js`, `session-domain.js`, `study-plan.js`, `companion-domain.js`, `profile-domain.js`, `privacy-domain.js` — alcance das seções do perfil, `tasks-domain.js`, `home-domain.js` — visões derivadas do Início, `slides-domain.js`, `subject-domain.js`, `pdf-domain.js`, `compression-domain.js`, `agenda-domain.js`, `settings-domain.js`, `backup-domain.js`, `merge-domain.js`, `xp-policy.js`, `schedule-domain.js` — cronograma derivado de `state.plan` e do progresso). O React (`src/`) e o Node as importam do mesmo arquivo; não duplique regra em `src/lib`.
- **A API é um app só (`api/`), com dois adaptadores:** `api/app.js` monta a tabela de rotas (`api/routes/*.js`), e cada rota declara método, caminho, se exige conta (`auth`), checagem de origem (`origin`) e limite de tentativas (`rateLimit`). `server.js` (Node + `node:sqlite`, estáticos de `dist/`) e `worker.js` (Cloudflare + D1 + R2) só adaptam banco (`api/adapters/sqlite.js`, `api/adapters/d1.js`, contrato `{ run, first, all, batch }`), imagens e variáveis; não contêm regra de rota. Erros de domínio estendem `AppError` (`api/errors.js`) e viram `{ error, code, field? }` num só lugar. Regras ficam nos módulos compartilhados: `api/domain/auth.js`, `api/domain/progress.js`, `api/domain/rewards.js`, `api/domain/commands.js`, `api/domain/import-server.js`, `api/domain/companion.js`, `api/domain/friends.js` (inclui o perfil entre amigos), `api/domain/xp.js` (livro `xp_events` e ranking), `api/domain/state.js` (estado com revisão otimista), `api/domain/messages.js` e `api/domain/message-extras.js` (citar, reagir, GIF e silenciar, em conversas privadas e grupos), `api/domain/email.js` (Resend; sem configuração, o link de redefinição só vai para o log), `api/domain/media.js` (avatar/header em R2 no Worker via `env.MEDIA`, `data/media/` no Node) e `public/*-domain.js`. O teste `tests/unit/api-contract.test.js` roda o mesmo roteiro HTTP no Node e no Worker (`wrangler dev` local).
- **XP validado no servidor:** os valores vigentes ficam em `public/xp-policy.js` (`XP_VALUES`, `LEVEL_XP`, blocos de tempo, teto diário). O cliente atual usa `/api/library/actions`; `library-actions.js` avalia `RULES` de `rewards.js` e grava progresso, XP e conquistas no mesmo batch. `library-time.js` prepara o tempo elegível para esse batch, e `library-subtasks.js` o XP de subtarefa concluída (10 XP uma vez por subtarefa, teto de 50 XP/dia). O horário do cliente só pode atrasar uma conclusão. `api/domain/xp.js` guarda o livro `xp_events`, correção e ranking. `/api/progress` e `/api/xp/complete|bonus|slides|time` são compatibilidade para contas não convertidas; contas convertidas recebem `client_outdated`. O saldo legado continua separado, fora do nível novo e do ranking.
- **Tempo real (mensagens):** `GET /api/realtime` abre um WebSocket só com avisos (`{ type: 'message', from }`); os dados continuam vindo das rotas HTTP. O app recebe a porta `realtime` (`{ notify, connect }`): no Worker é o Durable Object `UserChannel` por pessoa (`api/adapters/realtime-do.js`, binding `CHANNEL` e migration SQLite em `wrangler.jsonc`; a classe é exportada por `worker.js`); no Node são conexões em memória com a biblioteca `ws` (`api/adapters/node-realtime.js`, upgrade tratado em `server.js`). `announce` (`api/realtime.js`) nunca derruba a operação que avisa. No cliente, `src/lib/realtime.js` reconecta com espera crescente e batimento `ping`/`pong`; com o canal aberto, o polling de mensagens cai para 60 s (reserva), sem ele volta a 5–10 s. O contrato roda o mesmo roteiro nos dois alvos.
- **`server.js` aplica todos os `migrations/*.sql` no boot** (`applyMigrations` em `api/adapters/sqlite.js`), em ordem alfabética; para D1 é `npx wrangler d1 migrations apply lume --remote`. Nunca edite migração já aplicada — crie o próximo número.
- **O servidor lê `dist/` e o CSP uma única vez ao iniciar**; depois de `npm run build`, reinicie `server.js` para servir a versão nova.
- **Estado:** a API entrega v3 com materiais/unidades. Progresso é só `state.progress` (origem e `revertedAt`); use `isCompleted`/`completedUnitIds`, nunca listas paralelas. `restoreState` valida v3 por material/registro e recusa versões anteriores. O cliente não persiste estudo em localStorage. Revisão conflitante pede recarga. A tarefa em foco na Hoje é o campo de conta `focusTaskId` (regras em `tasks-domain.js`; `restoreState` descarta foco em tarefa concluída ou inexistente). `backup-domain.js` permite mesclagem explícita de arquivo v3, não sincronização entre dispositivos.
- **Cores são tokens com função** em `src/styles/00-tokens.css`, por tema (`data-theme`; escuro é o padrão). Há uma só paleta: o campo `palette` dos dados é aceito só por compatibilidade e não muda as cores. `--action` botão principal (dourado), `--lume` destaque, links e navegação (azul-claro), `--mint` progresso (azul-claro), `--success`, `--reward` XP, nível e "hoje" (dourado), `--warning` só atraso (coral), `--danger` erro, `--xp-from`/`--xp-to` barra de XP, `--star`/`--trail`/`--grid-dot` para a estrela, o caminho percorrido e a malha do fundo. Letras: `--font-display` (Bricolage Grotesque, títulos e logo), `--font-sans` (Atkinson Hyperlegible Next, texto) e `--font-mono` (JetBrains Mono, números, datas e todo contexto gamificado), hospedadas em `public/assets/fonts/`. Não use cor fixa em componentes; misture tokens com `color-mix`. Espaçamento usa `--space-1`…`--space-6` e `--actions-gap`; campos em linha usam `.form-grid` (não `.field-row`, que fica só para rótulo + ação). Mensagens de validação usam `.form-error` (e `.form-error-block` para falhas de gravação com repetição); não crie `auth-error` ou variações locais. O logo é a estrela dourada de quatro pontas (`Logo`/`Star` em `ui.jsx`, `public/favicon.svg`) com o nome "Lume"; o broto e "Lume Academy" foram aposentados por decisão da responsável. A folha é empacotada pelo Astro (nome com hash), então não há `?v=` manual; a ordem dos `@import` em `src/styles/lume.css` é a ordem da cascata — não reordene sem conferir as telas.
- **CSP é hash exato** do `<script>`/`<style>` inline que o Astro emite em `dist/index.html` (`scripts/headers.mjs`). `script-src` não tem `'unsafe-inline'`: script inline injetado em runtime é bloqueado. `style-src-attr 'unsafe-inline'` libera só atributos `style`.
- **Service worker (`public/sw.js`)** usa stale-while-revalidate em assets da mesma origem (menos navegação e `/api/*`): quem já visitou vê a versão em cache uma vez e a atualização só aparece na visita seguinte. Ao alterar CSS/imagens locais, teste com service worker limpo.

## Armadilhas de configuração

- As variáveis têm o mesmo nome no Node e no Worker (`api/config.js`): `SHOW_RESET_LINK` (em `wrangler.jsonc` é `"false"`), `ATTEMPT_LIMIT`, `BCRYPT_ROUNDS`. `LUME_SHOW_RESET_LINK` e `LUME_ATTEMPT_LIMIT` continuam aceitos como apelidos no servidor local.
- IA de organização é opcional e só no servidor: `LUME_AI_API_KEY` (fallback `OPENAI_API_KEY`), `LUME_AI_BASE_URL`, `LUME_AI_MODEL`. Sem chave, o organizador determinístico responde. Nunca exponha a chave no frontend nem em arquivos versionados.
- `ATTEMPT_LIMIT` vale 10 por padrão nos dois ambientes e limita cadastro, login e recuperação; importação (30), convites (20) e mensagens têm limite próprio por rota. Os e2e usam 1000 (a suíte cadastra mais de 200 contas em 10 minutos) e o teste de contrato usa 200.
- `BCRYPT_ROUNDS=6` no Worker é um compromisso com o limite de 10 ms de CPU do Workers Free e fica abaixo do mínimo 10 da OWASP. Não aumente sem medir (`node scripts/benchmark-auth.mjs 6`); a medição em produção continua pendente.
- Senhas novas: bcrypt até 72 bytes UTF-8, sem truncamento. Hashes PBKDF2 legados são preservados e migram só na redefinição de senha.
- `data/` é local e ignorado no Git (`data/lume.db` guarda as contas); não apague nem versione. Os e2e usam `data/e2e-<timestamp>`.

## Aplicativo de desktop (pacote `companion/`)

O aplicativo de desktop **é o Lume completo numa janela Electron**, com bandeja, presença opcional e atualização; presença não é o propósito dele. "Companion" é só o nome técnico (pasta, tags, endpoints). Em textos de produto, chame de "Lume" ou "aplicativo de desktop". Pacote npm separado em `companion/` (Electron + electron-builder, lockfile próprio): `npm install --prefix companion` uma vez; `npm run companion:app` abre a janela/bandeja e `npm run companion` roda o agente de terminal. `lume.cmd` na raiz é o iniciador. Configuração do usuário em `%APPDATA%\Lume\companion.json`, fora do repositório. `npm test` inclui `companion/update.test.js`; o CI também roda `node --check` nos arquivos do Companion. Release: suba `companion/package.json` e crie a tag `companion-v<versão>` — se não bater, o workflow falha. Detalhes em [Publicação e CI](docs/RELEASE.md); o que falta implementar está em [Funcionalidades pendentes](docs/IMPLEMENTACAO.md).

## Extensão do navegador (`extension/`)

A extensão MV3 importa cursos por clique (`activeTab`) e acompanha a reprodução de aulas importadas nos domínios que a pessoa autorizar no popup. `npm run extension:build` gera os scripts clássicos versionados `extension/capture.js` e `extension/watch.js` a partir de `extension/src/`, além do registro compacto de plataformas. Edite as fontes. O manifesto deve manter as permissões opcionais em acordo com `public/providers/registry.js`. Gran e Udemy têm leitores de grade e de conclusão por GET na própria plataforma. Preserve curso, aula e vídeo como identidades distintas. Importações continuam passando pela revisão do Lume.

O service worker registra o observador só após a autorização e conserva o estado por aba em `chrome.storage.session`. As rotas autenticadas `/api/extension/status`, `/api/extension/lesson` e `/api/extension/watch` aceitam a origem da loja ou da lista `EXTENSION_ORIGINS`. Em localhost, aceitam o ID de desenvolvimento. Para as consultas, o worker usa POST, que inclui Origin no Chrome. Preserve a checagem das demais rotas. Evidência, sessão e conclusão usam o batch da biblioteca e o XP vigente. Critérios e limites em [Regras de Negócio §11](docs/REGRAS_DE_NEGOCIO.md) e [manual da extensão](extension/LEIAME.md).

## Contexto obrigatório do produto

- Lume é uma plataforma social de estudos: biblioteca, continuidade de materiais, amigos, mensagens diretas, grupos de conversa, compartilhamento de aprendizados, conquistas e placares de estudo.
- Comunidades, servidores, canais públicos e ranking de grupos estão fora do escopo. O social se limita a amigos, mensagens diretas entre amizades aceitas, **grupos de conversa entre amigos** (decisão da responsável em 15/11/2026: 3 a 20 pessoas, só amizades de quem cria, sem bloqueio; `api/domain/groups.js`). **Colaboração em projetos e integração com GitHub foram aposentadas (16/11/2026):** saíram da interface e da documentação; `api/domain/collaboration.js`, as rotas `/api/collaboration/*` e a tabela `delivery_invites` ficam no servidor sem uso para não apagar dados, e material do tipo projeto continua como material individual. Não reintroduza. **Denúncias** (`api/domain/reports.js`, tela `#denuncias`) vão só para a conta criadora (`LUME_CREATOR_EMAIL`); quem denuncia nunca é revelada à pessoa denunciada.
- Cadastro e login com e-mail e senha são requisitos do Lume, assim como recuperação de acesso e saída da conta. A prévia local é temporária; não descreva como decisão de que o produto não terá login ou senha.
- A gamificação deve reconhecer avanço real: estudo efetivo, aula concluída, leitura concluída, curso concluído e entrega de projeto. Não premiar cliques ou movimentação na interface.
- Abrir uma janela, entrar no site, cadastrar um material, preparar a mesa, abrir uma aula, conectar uma conta, pausar ou enviar mensagens não gera XP.
- Apoios para começar e dividir uma tarefa continuam úteis, mas não são automaticamente eventos de recompensa. Não confundir preparação com conclusão de estudo.
- Tarefas não têm XP próprio. Concluir tarefa vinculada conclui a aula e usa sua recompensa validada no servidor uma única vez; sem vínculo, 0 XP. Disciplina completa concede 200 XP e conquista. Cargos são só títulos, sem bloquear funcionalidades.
- A inclusão de pessoas neurodivergentes é central. Personalização, conforto visual e pausas sem punição devem conviver com uma gamificação substancial e uma experiência social opcional.
- Não reduza o produto a um organizador individual de microtarefas, nem retire amigos ou placares por presumir que competição nunca pode ser inclusiva.
- O ranking é um recurso central obrigatório, com classificações por nível acumulado, cursos distintos concluídos e empenho no período. O recorte inicial é de amigos; não há ranking de grupos nesta etapa. Não o substitua apenas por um placar semanal de XP. Participação configurável não torna o desenvolvimento do ranking dispensável.
- Nenhum registro de atividade deve ser descrito como prova de compreensão, inteligência ou benefício clínico.
- O look and feel, os ícones e os textos da aplicação não devem ter nenhuma relação com "sustentabilidade", ecologia ou metáforas botânicas (não use termos como "sustentável", "cultivar", nem ícones como `sprout`, `leaf` ou `tree`). Use vocabulário direto de estudo: ritmo constante, ritmo equilibrado, construir o hábito e continuidade.

## Regras para implementar

- Preserve os dados existentes. A migração dos eventos antigos exige tratamento explícito; não apague progresso nem converta preparações antigas em aulas concluídas. O modelo legado em execução (5 XP por preparação, 10 XP por etapa, 10 XP por tarefa de prova, nível a cada 100 XP) não é a nova política e não pode alimentar ranking compartilhado.
- Separe recursos implementados, simulações locais e funcionalidades planejadas. A prévia sem conta e uma simulação de login no navegador não são autenticação. A API local já valida credenciais e emite sessão; isso não comprova publicação nem verificação do mesmo fluxo em produção. A sincronização de uma cópia do estado não equivale à validação de XP no servidor.
- Integrações devem declarar suas capacidades. Não prometa rastreamento automático de qualquer URL, videoaula, PDF, artigo ou repositório.
- Não coloque credenciais de integrações no frontend, em arquivos versionados ou em saídas de ferramentas. Não publique o conteúdo de repositórios privados por padrão.
- A atribuição de XP da versão com contas deve ser validada no servidor, com eventos identificáveis e proteção contra repetição. O navegador não deve ser a autoridade de um placar compartilhado.
- A lista de tarefas vive em `public/tasks-domain.js`; `library-actions.js` também aplica a conclusão vinculada no servidor. Reabrir tarefa não desfaz aula. Cargos permanecem nas pausas e são reavaliados nas correções. Atualize testes e `docs/REGRAS_DE_NEGOCIO.md` ao mudar essas regras.
- Os valores vigentes de balanceamento estão em `public/xp-policy.js` e documentados em `docs/REGRAS_DE_NEGOCIO.md`. Não espalhe valores contraditórios entre telas e regras de domínio.
- Ao mudar uma regra de produto, atualize os documentos afetados e os testes relevantes. Testes do protótipo não são justificativa para conservar uma regra já substituída.
- Ao receber tarefa só de documentação, documente as divergências; não aproveite para migrar dados, ativar serviços, alterar a pontuação ou publicar mudanças funcionais.
- Textos de interface, documentação e comentários: português do Brasil.

## Verificação e entrega

`npm test` para regras de domínio/autenticação; `npm run build` para validar a aplicação; `npm run test:e2e` para fluxos de interface afetados (rode o build antes, porque o Playwright serve `dist/`). O script `test` lista os arquivos um a um em `package.json`: ao criar um teste em `tests/unit/*.test.js`, inclua-o lá, senão ele não roda no CI. Módulos de servidor ficam em `api/domain/`; testes que precisam de banco usam `applyMigrations` e `sqliteAdapter` de `api/adapters/sqlite.js`. Os e2e rodam com paralelismo por arquivo (`fullyParallel: false`, `workers: process.env.CI ? 3 : 4`), `serviceWorkers: 'block'`, WebGL desabilitado e `BCRYPT_ROUNDS: '4'`; cada teste deve criar contas próprias com `crypto.randomUUID()`. O projeto `mobile` só roda testes marcados com `{ tag: '@celular' }` (layout, navegação, toque); marque um teste novo só quando o tamanho da tela mudar o que ele verifica, e prefira teste unitário para regras e rotas de API. A análise de link no e2e é interceptada por rota (simulação); extração real de plataformas não é exercitada. Mudanças apenas em documentação exigem revisão de coerência e links, sem repetir testes de código inalterado. Por decisão explícita da responsável, a interface não oferece modo essencial nem tratamento de movimento reduzido; os campos antigos permanecem apenas para compatibilidade dos dados.

Na entrega, informe o que mudou, o que foi verificado e o que ainda não está implementado. Não chame um recurso de concluído com base apenas em sua aparência.
